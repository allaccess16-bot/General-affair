### 3.1 모듈형 구조 (확장성)

각 업무 모듈은 **같은 폴더 규칙**을 따르고, 공통 셸은 모듈 등록 정보만 읽어 메뉴를 구성합니다. 향후 인사 모듈 등은 폴더 하나와 DB 스키마 하나를 추가하는 방식으로 붙입니다.

```
src/
  app/
    (portal)/
      dashboard/            # A. 통합 대시보드
      ga/                   # B. 총무 업무 지원
      vehicle/              # C. 법인차량
      meeting/              # D. 회의실
      seal/                 # E. 인장 날인 (신규)
      admin/                # F. 통합 관리자 센터
    api/                    # Route Handlers (Excel 다운로드, 첨부 서명 URL 등)
    login/
  modules/
    <module>/
      manifest.ts           # 메뉴명, 아이콘, 경로, 필요 권한, 대시보드 위젯
      components/
      server/               # 데이터 접근 함수 (DB 직접 접근은 여기서만)
      schemas.ts            # Zod 스키마
  core/
    auth/  rbac/  audit/  ui/  excel/  status/
supabase/
  migrations/               # 번호가 붙은 SQL 마이그레이션
  seed/                     # 테스트 데이터 (운영 미적용)
  tests/                    # RLS·제약조건 테스트
```

## 4. 기존 시스템 통합 방식

### 4.1 단계적 이행 (Strangler 방식)

| 단계 | 내용 | 기존 시스템 |
|---|---|---|
| ① 병행 | 통합 포털 오픈, 신규 인장 모듈만 실사용. 기존 3개 모듈은 메뉴에서 기존 URL로 연결 | 정상 운영 |
| ② 이관 리허설 | 스테이징 DB에 기존 데이터 이관 → 건수·합계·샘플 대조 검증 | 정상 운영 |
| ③ 모듈 전환 | 모듈별로 통합 UI 전환 (회의실 → 총무 → 차량 순 권장, 근거: 회의실은 Supabase라 이관 위험이 가장 낮음) | 읽기 전용 전환 |
| ④ 종료 | 일정 기간 읽기 전용 유지 후 종료 (최종 백업 보관) | 종료 |

### 4.2 데이터 연결 방식 후보 (시스템별 선택)

| 방식 | 설명 | 적합한 경우 |
|---|---|---|
| A. 일괄 이관 | 기존 DB → 통합 Supabase로 1회 이관 후 전환 | 기존 DB가 Supabase/PostgreSQL이고 구조가 명확한 경우 |
| B. 어댑터 조회 | 통합 앱이 기존 저장소를 API로 계속 읽음 | 이관이 어렵거나 당분간 기존 시스템 유지가 필요한 경우 |
| C. 이관 + 동결 | 과거 데이터는 이관, 기존 시스템은 읽기 전용 | 장기 이력 보존이 필요한 경우 |

**회의실:** 기존 Supabase 프로젝트를 그대로 통합 DB로 쓸지, 새 프로젝트로 옮길지는 스키마 확인 후 결정합니다. 기존 운영 프로젝트에 `core`/`seal` 스키마를 바로 추가하는 방식은 **기존 운영 DB를 직접 변경**하게 되므로, 기본 권장안은 **신규 통합 프로젝트 + 이관**입니다.

### 4.3 이관 시 원칙

- 기존 PK는 `legacy_id` 컬럼으로 보존하고, 통합 PK(UUID)는 새로 발급 → 원본 추적 가능
- 이관 스크립트는 **멱등**(여러 번 실행해도 중복 없음): `unique (legacy_source, legacy_id)` 제약
- 신청자 매핑: 기존 데이터의 신청자 값(이름/이메일/사번) → `core.employees.id` 매핑표 작성, 매핑 실패 건은 별도 목록으로 보고 후 수작업 확정
- 검증: 테이블별 행 수, 기간별 건수, 예약 시간 합계, 무작위 샘플 50건 필드 단위 비교 → 검증 보고서

## 5. 공통 사용자·권한 체계

### 5.1 인증 ❓

| 후보 | 설명 |
|---|---|
| Supabase Auth (이메일 + 비밀번호 / 매직링크) | 가장 단순. 사내 이메일 도메인 제한 가능 |
| 사내 SSO (SAML/OIDC: Azure AD 등) | 회사 계정과 일원화. Supabase SSO는 상위 요금제 필요 |

→ 기존 시스템의 로그인 방식과 회사 보안 정책 확인 후 결정합니다. 결정 전까지 설계는 `auth.users` ↔ `core.employees` 1:1 연결을 전제로 하며, 어떤 인증 방식을 택해도 이 연결 구조는 같습니다.

### 5.2 역할 (RBAC)

| 역할 | 설명 | 범위 |
|---|---|---|
| `employee` | 일반 직원 | 본인 신청·예약 조회/작성 |
| `ga_staff` | 총무 담당자 | 배정받은 업무 처리 |
| `module_manager` | 모듈 관리자 | 지정 모듈 전체 조회·관리 (모듈 단위로 부여) |
| `seal_approver` | 인장 승인자 | 지정된 인장·승인 단계의 승인/반려 |
| `seal_keeper` | 인장 관리(날인 처리)자 | 승인 완료 건의 실제 날인 완료 등록 |
| `system_admin` | 시스템 관리자 | 전체 조회, 사용자·권한·공지·코드 관리 |

- 권한은 `core.user_roles(employee_id, role, module_key, seal_type_id)`로 부여 → 모듈별·인장별 범위 지정 가능
- **화면 + API + DB(RLS) 3중 적용.** 화면에서 버튼을 숨기는 것은 편의일 뿐이고, 실제 차단은 RLS와 DB 함수에서 합니다.

## 6. 데이터 모델 초안

> 아래는 **신규 테이블(core, seal) 설계 초안**입니다. 기존 시스템 테이블(ga, vehicle, meeting)은 스키마 확인 후 설계하며, 지금 단계에서 임의로 정의하지 않습니다. 실제 SQL은 2단계에서 `supabase/migrations/`로 작성하고 **스테이징에서만** 먼저 적용합니다.

### 6.1 core (공통)

| 테이블 | 주요 컬럼 |
|---|---|
| `departments` | id, code, name, parent_id, is_active, sort_order |
| `employees` | id, auth_user_id(unique), employee_no(unique), name, email, department_id, position, phone, is_active |
| `user_roles` | id, employee_id, role, module_key(null=전체), seal_type_id(null=전체), granted_by, granted_at |
| `notices` | id, title, body, is_pinned, publish_from, publish_to, created_by |
| `notifications` | id, employee_id, module_key, ref_id, message, read_at |
| `audit_logs` | id(bigserial), occurred_at, actor_id, module_key, entity, entity_id, action, before(jsonb), after(jsonb), ip, user_agent — **수정·삭제 불가** |
| `status_codes` | module_key, code, label, category(`waiting`/`in_progress`/`done`/`cancelled`) — 모듈별 상태를 대시보드 공통 분류로 매핑 |

**통합 "나의 신청 현황"**: 모듈별 테이블을 `core.v_my_items` 뷰(UNION)로 묶습니다. 컬럼: `module_key, item_id, title, requested_at, scheduled_at, status_code, status_category, requester_id`. 뷰는 `security_invoker = on`으로 만들어 각 원본 테이블의 RLS가 그대로 적용되게 합니다.

### 6.2 seal (인장 날인, 신규)

| 테이블 | 주요 컬럼 |
|---|---|
| `seal_types` | id, name(예: 법인인감, 사용인감, 대표이사 직인 등 — 관리자 등록), description, keeper_dept_id, requires_attachment, is_active, sort_order |
| `seal_approval_steps` | id, seal_type_id, step_no, step_name, approver_role / approver_employee_id, is_required — **인장별 승인 단계 설정** |
| `seal_requests` | id, request_no(unique, 자동), requester_id, department_id(신청 시점 스냅샷), seal_type_id, purpose, document_name, submit_to(사용처/제출처), needed_date, quantity, remarks, status, current_step, assignee_id(처리 담당자), approved_at, sealed_at, sealed_by, created_at, updated_at |
| `seal_request_approvals` | id, request_id, step_no, approver_id, decision(`approved`/`rejected`), comment(반려 사유), decided_at — **추가만 가능** |
| `seal_attachments` | id, request_id, storage_path, file_name, mime_type, size, uploaded_by, uploaded_at |
| `seal_usage_ledger` | id, request_id(unique), seal_type_id, sealed_date, quantity, sealed_by, document_name, submit_to, requester_id, department_id — 날인 완료 시 자동 기록 |

**신청번호:** `SEAL-YYYYMM-0001` 형식. 월별 카운터 테이블 + DB 함수에서 행 잠금으로 발급(동시 신청 시 중복 없음).

**상태 전이 (승인 완료 ≠ 날인 완료):**

```
작성중(draft) ─제출─▶ 접수(submitted) ─검토 시작─▶ 검토중(in_review)
                         │                          │
                       취소(cancelled)◀─신청자 취소─┤ (날인 전까지만)
                                                    ├─ 모든 필수 단계 승인 ─▶ 승인완료(approved) ─날인 등록─▶ 날인완료(sealed)
                                                    └─ 어느 단계든 반려 ───▶ 반려(rejected)
```

- 상태 변경은 **DB 함수(`seal.submit`, `seal.decide`, `seal.complete_sealing`, `seal.cancel`)로만** 가능. 테이블 직접 UPDATE는 RLS로 차단
- 각 함수가 권한(해당 인장·단계의 승인자인지), 현재 상태, 단계 순서를 검증하고 감사 로그를 같은 트랜잭션에서 기록
- 인장 이미지 합성 기능은 **만들지 않음** (요구사항). 시스템은 신청·승인·기록만 담당

### 6.3 예약 충돌의 DB 수준 차단 (회의실·차량 공통 방식)

```sql
-- 기존 테이블 구조 확인 후 적용. 예시 형태만 제시.
create extension if not exists btree_gist;
alter table meeting.reservations
  add constraint no_overlap
  exclude using gist (room_id with =, tstzrange(start_at, end_at, '[)') with &&)
  where (status <> 'cancelled');
```

- 두 사용자가 동시에 같은 시간을 예약해도 DB가 한 건만 허용 → 요구사항 2.6 충족
- 반복예약은 개별 발생 건을 행으로 펼쳐 저장하고 `series_id`로 묶는 방식을 권장(충돌 검사가 위 제약으로 일관되게 동작). 기존 시스템의 저장 방식 확인 후 확정 ❓

## 7. 보안 설계

| 요구사항 | 구현 방식 |
|---|---|
| 신청자는 본인 신청만 기본 노출 | RLS: `requester_id = current_employee_id()` 또는 권한 보유자 |
| 권한 있는 담당자만 승인·처리 | 상태 변경 DB 함수에서 `user_roles` + `seal_approval_steps` 검증 |
| 승인 이력 변경 불가 | `seal_request_approvals`, `audit_logs`에 UPDATE/DELETE 권한 회수 + 차단 트리거 |
| 승인 완료와 날인 완료 분리 | 별도 상태(`approved` / `sealed`) + 별도 일시·처리자 컬럼 |
| 민감 첨부파일 보호 | Storage **private 버킷**. 서버 API가 권한 확인 후 **60초 유효 서명 URL** 발급. 공개 URL 사용 안 함 |
| 업로드 제한 | 허용 확장자(pdf, docx, xlsx, hwp, jpg, png 등 — 확정 필요), 파일당 용량 제한, 파일명 서버에서 재생성 |
| 서비스 키 보호 | `SUPABASE_SERVICE_ROLE_KEY`는 서버 전용 환경변수, 클라이언트 번들에 포함 금지. 사용처를 Excel 생성 등 최소 범위로 제한 |
| 감사 로그 | 신청·변경·승인·반려·취소·완료·권한 변경·Excel 다운로드 기록 |

## 9. 환경 분리 및 배포 (Vercel)

| 환경 | Vercel | Supabase | 데이터 |
|---|---|---|---|
| 개발 | 로컬 | 로컬(Supabase CLI) | 시드 데이터 |
| 스테이징 | Preview 배포 | **스테이징 전용 프로젝트** | 테스트 데이터 + 이관 리허설 데이터 |
| 운영 | Production 배포 | 운영 프로젝트 | 운영 데이터 |

환경변수(초안): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`(서버 전용), `NEXT_PUBLIC_APP_ENV`, `ALLOWED_EMAIL_DOMAIN`. 상세 가이드는 2단계 산출물로 작성합니다.

**백업:** 이관 직전 기존 DB 전체 덤프(구조+데이터) 보관 / 운영 Supabase는 일일 백업(요금제에 따라 PITR) + 주기적 `pg_dump`를 별도 저장소에 보관 / 복구 리허설을 스테이징에서 1회 이상 수행.

## 10. 단계별 진행 계획

| 단계 | 내용 | 선행 조건 |
|---|---|---|
| **1단계** (현재) | 기존 시스템 분석 + 통합 설계 초안 | — |
| 1단계 확정 | 자료 수령 후 01·02 문서 확정, 기능 추적표 작성 | 소스·스키마 수령 |
| 2단계 | Next.js 골격, 공통 UI 디자인 시스템, core 스키마 마이그레이션(스테이징), 인증 | 인증 방식 결정 |
| 3단계 | 통합 포털·대시보드 | 2단계 |
| 4단계 | 기존 3개 모듈 연결(어댑터 또는 이관 리허설) + 기능 동등성 검증 | 시스템별 연결 방식 결정 |
| 5단계 | 인장 날인 모듈 | 인장 종류·승인 단계 정책 확인 |
| 6단계 | 관리자 센터·통계·권한 관리·Excel | 3~5단계 |
| 7단계 | 데이터 검증, 보안·기능 테스트, 배포, 매뉴얼 | 전체 |

> 5단계(인장 날인)는 기존 시스템과 의존성이 없으므로, 기존 시스템 자료 수령이 늦어지면 **2단계 직후 우선 착수**할 수 있습니다.
