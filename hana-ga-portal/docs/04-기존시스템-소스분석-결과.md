## 1. 총무 업무요청 + 법인차량 (하나의 앱)

| 구분 | 확인 내용 |
|---|---|
| 형태 | 단일 HTML (Tailwind CDN, Chart.js, supabase-js v2) · 모바일 우선(max-w-md) |
| DB | Supabase 프로젝트(원본 HTML에 지정) · publishable key로 브라우저에서 직접 읽기/쓰기 |

| 인증 | 사용자 인증 없음 · 관리자 화면은 코드에 박힌 공용 비밀번호로 진입 |
| 갱신 | 30초 주기 전체 재조회 |

### 1.1 `requests` 컬럼 (코드에서 사용하는 필드)
`id, request_date, title, description, requester_name, department, contact, edit_password, location, category, urgency, status, assignee, admin_memo, completed_at, created_at, updated_at`

- 카테고리: 시설/비품 · 문서/행정 · 좌석/이전 · 출입증/보안 · 차량/출장 · 복리후생 · 계약/구매
- 긴급도: 보통 · 긴급 · 낮음 / 상태: 접수 · 검토중 · 진행중 · 완료 · 반려
- 요청자 조회: 이름·부서·연락처 부분일치 / 수정: 수정 비밀번호 확인 후 제목·상세·위치만
- 관리자: 상태·담당자·완료일·처리메모 저장, 삭제, 상태별 그래프 포함 상세 리포트(.xls)

### 1.2 `vehicle_reservations` 컬럼
`id, vehicle_name, vehicle_number, use_date, start_date, start_time, end_date, end_time, applicant, department, contact, driver, reservation_password, purpose, destination, status, complete_department, complete_name, odometer_before, odometer_after, total_distance, fuel_cost, parking_cost, etc_cost, complete_memo, completed_at, created_at, updated_at`

- 차량: K5 191호8366 · K5 191호8367(청라) · K5 146호9979
- 상태 흐름: 신청 → 승인(관리자) → 사용완료(사용자가 운행기록 작성) / 반려 · 승인 취소(승인→신청)
- 중복 규칙: 같은 차량의 `신청`·`승인` 건과 **일시 범위가 겹치면** 신청 불가 (같은 날이라도 반납시간 이후는 가능)
- 수정: `신청` 상태만, 예약 비밀번호 확인 / 운행기록: `승인` 건, 예약 비밀번호 확인, 주행거리 자동 계산
- 관리자: 승인·승인취소·반려·삭제, **업무용승용차 운행기록부(국세청 별지 서식) .xls** 전체/차량별 다운로드
- 공통 검증: 이름 2자 이상·자음만 불가, 연락처 2자 이상, 필수값 미입력 시 제출 버튼 비활성

## 2. 회의실 예약 V2.10

| 구분 | 확인 내용 |
|---|---|
| 형태 | 단일 HTML (자체 CSS) · 사이드바/모바일 하단 내비 · Cloudflare Pages 배포 |
| 설정 | `./config.js` → `window.HANA_MEETING_CONFIG` (supabaseUrl, supabaseAnonKey, businessStart/End, checkinGraceMinutes, refreshSeconds) — **파일 미제공** |
| DB 접근 | supabase-js 없이 REST 직접 호출 · 읽기: `rooms`, `reservations_public`(뷰) · 쓰기: **RPC만 사용** |
| RPC | `create_reservation`, `create_recurring_reservations`, `manage_reservation`(checkin/cancel), `manage_reservation_series`, `find_reservations_by_code`, `admin_verify`, `admin_cancel_reservation`, `admin_cancel_series`, `admin_set_room_active` |
| 인증 | 예약코드(8자리) 기반 본인 확인 · 관리자 비밀번호는 서버 RPC로 검증(브라우저 미저장) |
| 연결 장애 | 데모 전환 없이 예약 기능 잠금 + 15초 자동 재연결 |

- 회의실 12개: 12F 12-1~12-6, 13F 13-1~13-5 + 대회의실(30인) — 정원·위치·고유 색상
- 예약 상태: `reserved`(예약) · `checked_in`(사용 중) · `completed`(사용 완료) · `cancelled`(취소) · `no_show`(자동취소)
- 30분 단위, 08:00–20:00 / 단일 예약은 시작 후 10분 내 입실확인 없으면 자동취소 / 반복은 입실확인 없음
- 반복·장기: 시작일~종료일(제한 없음) × 요일, **1건이라도 충돌 시 전체 미생성**, 충돌 일정 상세 표시
- 화면: 대시보드(현재 상태 4지표·회의실 카드), 월간 캘린더(공실·예약률), 날짜별 예약, 회의실 7일 보기(빈 칸 클릭 예약), 내 예약(기기 저장·코드 조회), 관리자(강제취소·반복 전체취소·운영중지·30일 이용량/부서별), 이용 안내
- 서버(DB)에서 중복예약 차단 — 안내 문구 기준, 실제 제약 정의는 스키마 확인 필요

## 3. 보안 점검 결과 (통합 전 조치 필요)

| 등급 | 시스템 | 내용 | 권장 조치 |
|---|---|---|---|
| **높음** | 총무·차량 | `select('*')`로 **다른 사람의 `edit_password`·`reservation_password`까지 모든 브라우저에 내려옴** — 개발자도구로 누구나 열람 가능. 비밀번호 확인도 브라우저에서만 수행 | 비밀번호 컬럼을 조회 대상에서 제외(뷰/RLS), 확인은 서버 RPC로 이전, 통합 후에는 로그인 권한으로 대체 |
| **높음** | 총무·차량 | 관리자 비밀번호가 HTML에 평문으로 포함 · 삭제·상태변경이 publishable key로 직접 실행 | RLS 정책 확인 필요. 현재 정책이 허용한다면 **누구나 API로 삭제·승인 가능**. 관리자 작업은 RPC + 서버 검증으로 이전 |
| 중간 | 총무 | ‘내 요청 조회’가 이름·부서 일부만으로 다른 사람의 요청·연락처를 조회 | 로그인 사용자 본인 건만 노출 |
| 중간 | 공통 | 비밀번호 평문 저장 | 해시 저장 또는 폐지(로그인 전환) |
| 낮음 | 회의실 | 구조 양호 (RPC·뷰·서버 검증). 관리자 비밀번호를 RPC 인자로 매번 전송 | 통합 시 역할 기반 인증으로 대체 |

> 위 항목은 **소스 기준 판단**입니다. Supabase RLS 정책을 확인하면 실제 노출 범위를 확정할 수 있습니다.
